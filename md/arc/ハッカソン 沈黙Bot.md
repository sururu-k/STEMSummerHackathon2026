# 沈黙アプリ（本命案）

テーマ「隙間」→ 会話の隙間 → 沈黙を計測して、誰が会話を止めたかを特定する。

**方針変更: Discord Bot ではなく Web アプリを本線にする。** 理由は下の「なぜWebが勝つか」。

## 一行説明

**発言の中身は一切送らず、「喋った / 喋っていない」の1bitだけを持ち寄って、会話の隙間を可視化する。**

## なぜWebが勝つか

| | Discord Bot | Web アプリ |
|---|---|---|
| 審査員の参加 | VCに入ってもらう必要がある | QRを読ませるだけ |
| 対面の会話 | 使えない | **使える** |
| API リスク | 音声受信は非公式サポート。当日壊れうる | ブラウザ標準APIのみ。壊れない |
| プライバシー | botに音声が渡る | **音声が端末から出ない** |
| 説明のしやすさ | Discord前提の説明が要る | URLを開くだけ |

ハッカソンは対面。審査員はその場にいる。**Discordに入ってもらうより、QRを配って全員のスマホを開かせる方が速いし、絵になる。** ここが決定打。

## 構造

参加者それぞれが自分の端末でページを開く。**1端末 = 1人のマイク**。これで話者の特定問題が消える。

```
各端末: マイク → ブラウザ内でVAD → { speaking: true/false, level: 0.42 } を 10Hz で送信
                                    ↑ 音声そのものは一切送らない
サーバー: 全員の状態を集約 → 沈黙区間を検出 → 表示用クライアントにブロードキャスト
大画面: タイムライン + 沈黙カウンタ + 「止めた人」
```

### 同室のクロストーク対策（技術的な見せ場）

対面だと、隣の人の声も自分のマイクに入る。これを **端末をまたいだ音量比較** で解く。

同時刻に複数端末が「喋っている」と判定したら、**level が最大の端末の持ち主が実際の話者**。自分の声は自分のマイクで圧倒的に大きいので、これだけでほぼ分離できる。

分散マイクアレイでダイアリゼーションをやっている、と言える。手法として説明できる形になっているのが強い。

## VAD の実装

素直にやる。ライブラリ不要。

1. `getUserMedia` でマイク取得
2. `BiquadFilterNode` で 300〜3400 Hz にバンドパス（エアコン、机の振動、キーボードを落とす）
3. `AudioWorkletProcessor` の中で RMS を計算する。**`AnalyserNode` をタイマーでポーリングしない** — 非アクティブタブでスロットリングを食う。Worklet はオーディオスレッドで走るので影響を受けない
4. **適応ノイズフロア**: 直近数秒の RMS の下位パーセンタイルを暗騒音とみなし、閾値 = フロア + マージン。部屋ごとの音量差を吸収する
5. **ヒステリシス**: 発話開始の閾値 > 終了の閾値。パタパタしなくなる
6. **最小発話長**（例 200ms 未満は無視）と **ハングオーバー**（例 300ms 未満の途切れは繋ぐ）

これで足りなければ、ブラウザで動くニューラルVAD（Silero VAD を ONNX Runtime Web で回すパッケージがある。要確認）に差し替えるだけで済むよう、VADは1関数に閉じ込めておく。

### 時刻の扱い

端末の時計は信用しない。**サーバー到着時刻で統一する。** 通信遅延は数十ms、対して測りたい沈黙は秒スケールなので誤差は無視できる。ここを凝ると時間を溶かすので凝らない。

## コア機能

### 1. 会話ストッパー検出

発話終了から次の発話開始までの間隔を全部記録。閾値（例 3秒）を超えた沈黙について、**直前に喋っていた人**を記録する。

- 「〇〇さんの発言後、平均 7.2 秒の沈黙が発生します（全体平均 2.1 秒）」
- ストッパーランキング
- 逆側の **沈黙ブレイカーランキング**（止まった会話を再開した人）を必ず出す。**これが設計上の要。** ストッパーだけ晒すと吊るし上げになって誰も使わなくなる。破る人が実質MVP

### 2. 沈黙タイムライン

誰がいつ喋ったかをガントチャート状に描く。喋っている帯と、その間の空白。**空白の面積がそのまま「隙間」**。1枚絵として一番強いので大画面のトップに置く。

### 3. リアルタイム沈黙カウンタ

全員が黙った瞬間から数字が立ち上がる。3秒、5秒、10秒で表示が変わる。**デモで確実に発火する**ので見せ場はここ。

### 4. 介入モード（余力があれば）

沈黙が N 秒続いたらアプリが話題を投げる。検出だけでなく埋めにいく。

### 5. 沈黙の再生（オプトイン）

沈黙区間だけを繋いだ音声を出力する。「本日の沈黙、合計11分」。

ポイントは **沈黙は無音ではない** こと。息、椅子の軋み、キーボード、エアコン。繋いで聴くと生活音だけが残る。体験として一番刺さる部分。

ただしこれだけは音声の実データが要る。機能1〜4の「音声を送らない」設計と真っ向から矛盾するので、**明示的なオプトインで完全に分離する**。デモでやるなら自分たちの録音で見せる。

## 技術構成

| 層 | 選択 |
|---|---|
| クライアント | 素の HTML + Web Audio API（getUserMedia / BiquadFilter / Analyser） |
| 通信 | WebSocket、10Hz で `{speaking, level}` のみ |
| サーバー | Node + ws。部屋の状態はインメモリで十分 |
| 表示 | Canvas でタイムライン。別URLで大画面用ビュー |
| 保存 | SQLite（後から振り返る用。デモには不要） |

依存が極端に少ない。**1日で作り切れる規模。**

## PR動画をローカルで撮る場合

**方針: 本番前に localhost で収録する。動画はモックで十分。**

実マイクを通した絵が不要なら、下の「壁」と1〜4の作り分けは丸ごと不要。ハードコードしたイベント列でUIを animate するだけのモックを作って撮ればよい。以下は実データで撮りたくなった場合の参考として残す。

localhost はセキュアオリジンなので `getUserMedia` がそのまま通る。トンネルもデプロイも不要。ただし**別の壁**が出る。

### 壁: 1台のPCにマイクは1本しかない

このアプリは「1端末 = 1人」が前提。1台のPCで複数タブを開いても、全タブが**同じ物理マイクの同じ音**を聞くので、話者の出し分けができない。音量比較も全員同値になって機能しない。

解き方は4つ。上から順に堅い。

**1. リプレイモード を作る（推奨）**
セッションのイベント列（誰がいつ喋り始めて、いつ止めたか）を JSON で保存し、それを再生できるモードを付ける。

- 一度だけ本物のデータを取れば、以降は**何テイクでも完全に同じ絵が再現できる**
- 撮り直しがタダになる。ナレーションと尺を合わせ込める
- 開発中の動作確認にもそのまま使える。マイクに向かって喋らずにUIを詰められる
- 本番当日、万一マイクが全滅してもこれで乗り切れる**保険になる**

作るコストが低くて見返りが大きいので、これは動画のためだけでなく**最初から実装する**べき。

**2. 仮想オーディオデバイスで別々の音を流し込む**
Windows なら VB-CABLE / VoiceMeeter で仮想入力を複数生やす。`getUserMedia({audio: {deviceId}})` でタブごとに別デバイスを指定できるので、各タブに別々の音声トラックを食わせられる。実際に音声処理を通した本物の絵が撮れる。

**3. Chrome のフェイクデバイスに wav を食わせる**
`--use-fake-device-for-media-stream --use-file-for-fake-audio-capture=話者A.wav` でマイク入力を wav に差し替えられる。`--user-data-dir` を分けて Chrome を人数分起動すれば、決定論的な多人数入力になる。（フラグの正確な綴りは要確認）

**4. 素直にノートPCを人数分並べる**
LAN IP になるので非セキュアオリジンでマイクが取れない。回避するなら Chrome を
`--unsafely-treat-insecure-origin-as-secure="http://192.168.x.x:3000" --user-data-dir=別ディレクトリ`
で起動する。収録用の閉じた環境なら許容範囲。

### 収録時の実装上の注意

**バックグラウンドタブは時計が止まる。** 1台で複数タブを開いて撮るなら致命的。`setInterval` は非アクティブタブで 1Hz まで絞られ、`requestAnimationFrame` は停止する。

対策は **VAD を `AudioWorkletProcessor` に置くこと**。オーディオスレッド上で走るのでタブのスロットリングを受けない。精度の面でも `AnalyserNode` をポーリングするより素直なので、**最初からこちらで書く**。

タブでなく別ウィンドウにして全部見える位置に並べる、という手もあるが、Worklet にしておけば悩まなくて済む。

### 撮っておきたい画

1. QRを読んで参加者が増えていくところ（本番の体験がそのまま伝わる）
2. 雑談中、タイムラインの帯が伸び続けている俯瞰
3. **全員が黙った瞬間**。カウンタが立ち上がるところは寄りで撮る
4. 「この沈黙を作ったのは〇〇さん」の名指し
5. セッション終了後の集計画面

3が山場なので、**沈黙が始まってからの数字の動き**を一番丁寧に見せる。音声も一緒に録って、実際に「音が消える」体験を視聴者にさせる。

画面収録は OBS。ブラウザ音声とマイクを別トラックで録っておくと編集で救える。

## 当日詰まるポイント（先に潰す）

- **getUserMedia は HTTPS 必須**。localhost は例外だが、参加者のスマホからLAN IPで叩くと非セキュアオリジンで**マイクが取れない**。ngrok / cloudflared でトンネルを立てるか、どこかにデプロイしておく。**これを当日やると死ぬので前日までに確定させる**
- **iOS Safari**: AudioContext はユーザー操作を起点にしないと started にならない。必ず「開始」ボタンを踏ませる。画面ロックやタブのバックグラウンド化でマイクが切れるので、**画面を点けたままにしてもらう**案内をUIに出す
- マイク許可を拒否された人のフォールバック（観戦モード）を用意しておく
- 会場が騒がしいと適応ノイズフロアが上がりきる。**閾値マージンを画面から手で動かせるスライダー**を1本出しておくと当日救われる

## デモ台本

1. スクリーンにQRを出す。審査員が読む
2. 全員「開始」を押す。名前を入れる
3. 雑談してもらう → タイムラインがリアルタイムで伸びる
4. わざと全員黙る → 沈黙カウンタが立ち上がる
5. 「この沈黙を作ったのは〇〇さんです」と名指しする
6. その場のセッションの集計を出す

**審査員自身が被験者になる。** これが最大の武器。

## 深掘りの一手（審査で効く）

会話の話者交代の間隔は言語学で実測されていて、言語を越えて概ね数百ミリ秒に収束するという研究がある（Stivers et al. 2009, PNAS の10言語比較。**数値は要確認**）。

これを基準線に置くと「対面の標準 vs オンラインの実測」を並べられる。**オンラインの会話は伝送遅延と発話衝突の回避のぶんだけ隙間が広い**という仮説を自前データで示せれば、テーマ「隙間」への回答として一段上がる。

沈黙を悪者にしない整理も持っておく。

- 良い沈黙: 思考の間。沈黙後に話題が深まる
- 悪い沈黙: 気まずさ。沈黙後に話題が変わる、または誰も喋らないまま解散

沈黙の直後に同じ話題が続いたか変わったかで、機械的に分けられる。

## Discord 版の扱い

**捨てないが、本線から降ろす。** テキストチャンネル版はメッセージのタイムスタンプ差分だけで済み、実装が数十分で終わるので、余力で足す小ネタとして持っておく。

- 「このメッセージで会話が3時間止まりました」→ 自動でリアクションを付ける
- 週間「会話終了メッセージ」殿堂
- **無反応メッセージの供養**: 返信もリアクションも付かずに流れたメッセージを集める。これも立派な「隙間」

VC版（`connection.receiver.speaking` を使う案）は、Discordがbotの音声受信を公式サポートしていない以上、当日壊れるリスクを負うだけなので**やらない**。

## ホスティング（Pages / VPS 生IP）

**結論: モックは Pages でよい。本番アプリは生IP直叩きだと動かない。**

分岐は「マイクを使うか」の一点。

| | マイク不要（モック） | マイク必要（本番） |
|---|---|---|
| GitHub Pages | 最適。HTTPS付き・静的・無料 | 静的なのでWebSocketサーバを置けない |
| VPS 生IP (http) | 動く | **getUserMedia が拒否される** |
| VPS + ホスト名 + TLS | 動く | 動く |

### 生IPが詰む理由

`getUserMedia` は secure context 限定。`http://203.0.113.10:3000` は非セキュアオリジンなので、**スマホでは例外なくマイクが取れない**。デスクトップChromeなら起動フラグで抜けられるが、審査員のスマホには当然使えない。QRを配る導線が丸ごと死ぬ。

`https://` を生IPで張るのも素直にはいかない。IPアドレス向けの証明書は長らく発行できず、Let's Encrypt が対応を始めたという話はあるが短命証明書のプロファイル前提で制約がある（**要確認**）。ここで時間を溶かす価値はない。

さらに、Pages(https) から VPS(ws://) を叩く構成も **mixed content でブラウザにブロックされる**。結局 `wss://` が要る＝有効な証明書が要る、に戻る。

### 現実的な解（上から順に楽）

1. **Cloudflare Tunnel** — VPSに `cloudflared` を入れるだけで HTTPS のホスト名が生える。証明書の管理も、ポート開放も、DNS設定も不要。ハッカソン用途ではこれが最短
2. **nip.io / sslip.io** — `203-0-113-10.nip.io` のように IP をそのまま名前解決してくれるワイルドカードDNS。ホスト名ができるので Let's Encrypt が普通に取れる。ドメイン購入不要。ただし共有ドメインなのでレート制限に当たることがある
3. **安いドメインを1本買う** — 数百円。一番揉めない。時間があるならこれ

いずれにせよ **静的配信と WebSocket を同一オリジンに寄せる**（nginx で `/` は静的、`/ws` は Node にリバースプロキシ）。CORS も mixed content も考えなくてよくなる。Pages と VPS に分けても得がないので分けない。

### 実際の運用

- **モック / PR動画** → Pages。静的HTML一枚、マイクもサーバも使わない。URLも配りやすい
- **本番の live デモ** → VPS + Cloudflare Tunnel。前日までに一度スマホで開いてマイク許可まで通しておく
- **保険** → 本番URLでもリプレイモードを叩けるようにしておく。回線が死んでもモックと同じ絵は出せる
